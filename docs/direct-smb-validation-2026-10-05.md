# 직접 SMB 구현·검증 기록

2026-10-05 · Resonance 0.3.0 (3) · macOS arm64 · 설치 경로 `~/Applications/Resonance.app`

## 구현

- AMSMB2 **4.0.3** (`1726aaaf7adf63d7d1d2a0c5d1b0e635028215c0`)와 포함된 libsmb2를 고정했다. Context7 조회 후 해당 버전의 실제 `AMSMB2.swift`, `FileHandle.swift`를 검토했다. `contents(range:progress:)`는 요청 범위까지만 읽으며 현재 구현은 명시적 64 KiB 이하 태그 요청을 사용한다. 공유 연결을 재사용하고 actor 내부 gate로 라이브러리 호출 전체를 직렬화한다.
- 스캔과 재생은 별도 연결 pool을 사용한다. 스캐너에서는 재생 캐시와 CLI를 호출할 수 없다. FLAC 태그 스캔은 STREAMINFO/VORBIS_COMMENT만 읽으며 PICTURE/PADDING/SEEKTABLE을 건너뛴다. 기본 읽기 상한 2 MiB, 메타데이터 영역 64 MiB, 512블록, 60초의 파일별 제한과 15초 SMB 응답 제한이 있다.
- 원격 경로는 서버 이름 그대로 저장한다. `Data(utf8)` 기반 조회·coverage와 원본 바이트 해시로 NFC/NFD 경로를 구분하며, 상위 경로·NUL·구분자 혼동은 거부한다. 파일명을 임의로 정규화해 다시 시도하지 않는다.
- `LibraryRoot.smb`를 추가하고 root/path/album/track ID는 유지한다. v7 migration 및 소스 전환 전 SQLite backup을 만들며 소스 전환은 transaction에서 수행한다. 기존 로컬 폴더 접근으로 되돌릴 수 있다.
- 변경 없는 파일은 크기·수정 시각으로 재사용한다. 부분 디렉터리 실패는 스캔 미완료로 남기며 기존 원격 루트의 누락 정리를 하지 않는다. 파일 태그 실패 경로도 보호한다. 파일별 성공 읽기량·요청수·시간·지원 상태는 `smbReadMetric`, 실패 경로는 scanRun에 저장한다. 읽기량은 SMB payload의 논리적 파일 데이터이며 실제 패킷 전송량이 아니다.
- 현재 곡을 완전히 캐시한 뒤 재생을 시작하고 다음 한 곡을 별도 task로 준비한다. generation/개별 waiter 취소/lease로 큐 변경과 공유 다운로드를 처리한다. 4 GiB 캐시, 디스크 여유 공간, 다운로드 전후 버전, 크기, 완료 파일 SHA-256, 원자적 공개와 재시작 partial 정리를 적용했다. 태그 파싱 성공은 전체 오디오 무결성 검증으로 간주하지 않는다.
- 앨범을 열 때만 외부 이미지 또는 제한된 내장 커버를 요청한다. 기존 커버·부클릿 연결 데이터는 유지한다. FLAC 이외의 직접 SMB 태그 파서는 이번 버전에 없으며 기본 항목/기존 태그를 유지하고 보류 상태를 저장한다. 기존 로컬 파서는 그대로 사용한다.
- 동적 `libAMSMB2.dylib`를 `Contents/Frameworks`에 포함하고 앱 상대 rpath를 추가했다. 라이브러리를 먼저 서명한 뒤 앱을 서명한다. LGPL 고지·라이선스·해당 라이브러리 소스와 SwiftPM manifests를 앱에 포함했다. 설치 앱은 Homebrew 또는 `smbclient`를 실행하지 않는다.

## 실제 라이브러리 복구와 후속 수정

사용자가 보여 준 “파일 없음” 목록은 오전 마운트 스캔의 기록이었다. 첫 구현에서는 직접 SMB 기능과 별도 진단 DB의 검증을 완료했지만 운영 라이브러리 전체 재스캔을 끝내지 못했다. 실제 오류 목록까지 해결되었다고 볼 수 없는 상태였다.

추가로 직접 SMB 스캐너가 개별 파일 오류나 미지원 형식 하나만 있어도 전체 순회를 미완료로 취급하여 과거 오류 목록이 계속 합쳐지는 버그를 확인했다. 디렉터리 순회 실패·취소와 개별 파일 오류를 구분하도록 수정했다. 정상적으로 끝난 순회는 현재 오류 목록으로 교체하며, 개별 실패 파일과 불완전 디렉터리는 기존 기록을 보존한다. 회귀 테스트에서 복구된 파일의 과거 오류가 사라짐을 확인했다.

- 변경 없는 SMB 파일을 재사용할 때 로컬 커버 캐시 유무를 조건으로 삼던 문제를 수정했다. 커버가 없어도 음원 태그를 다시 읽지 않으며, 커버는 앨범을 열 때 요청한다.
- `searchGram(docID)` 인덱스 누락 및 진행 갱신마다 전체 컬렉션을 계산하던 병목을 수정했다. v8 마이그레이션이 `searchGram(docID)` 인덱스를 추가한다. 최종 정리 단계 프로파일에서 앨범마다 `searchContent` 전체를 읽는 것을 추가 확인했고, v9에 `searchContent(albumID)` 인덱스를 추가했다.
- ID3v2 태그가 FLAC 스트림 앞에 있는 음원의 호환성을 추가했다. 길이 필드로 태그 본문을 건너뛴 뒤 FLAC 메타데이터만 읽는다. ID3v2.2/2.3/2.4, footer, 잘못된 길이, 대용량 태그 건너뛰기를 테스트했다. Bloch 19곡(7,186 bytes)과 Schnittke 11곡(3,671 bytes)은 수정 빌드에서 모두 직접 SMB 색인·반복 재사용에 성공했다.
- ID3v2+ID3v1로 감싼 FLAC의 경우 Core Audio가 마지막 패킷에서 실패하는 것을 재현했다. 완전히 받은 비공개 staging 캐시에서만 ID3 포장을 제거하며 FLAC 메타데이터·오디오 바이트는 그대로 보존한다. 원본 크기/버전 확인은 변환 전에 수행하고, 캐시에는 원본 크기·변환 후 크기·SHA-256 영수증을 저장한다. 재시작 재사용과 변조 탐지, 2 MiB 이상 바이트 보존을 테스트했다. 이후 실제 Bloch 19곡을 SMB로 다시 받아 모든 선언 샘플 수와 디코딩 샘플 수가 같고 캐시가 재사용됨을 확인했다. 19개 변환 캐시의 외부 `flac --test --silent`도 전부 통과했다. 같은 방식으로 Schnittke 11곡도 전체 선언 샘플 수·캐시 재사용·외부 FLAC 무결성 검사에 모두 성공했다.
- 실제 캐시 파일로 AVQueuePlayer의 seek 후 EOF 초과를 재현했다. STREAMINFO 샘플 길이에 따른 `forwardPlaybackEndTime` 설정 후 같은 캐시 파일에서 끝 이벤트와 다음 곡 전환을 확인했다.
- 스크린샷의 Anna Prohaska / Haffner-Akademie 05번을 실제 앨범 화면에서 선택해 직접 SMB 캐시 후 X100 출력 재생이 시작됨을 확인했다. 05·06·14번 모두 운영 DB의 `metadataStatus=complete`, `available=true`다.
- 실제 앱에서 X100-00432f-USB 출력으로 트랙 04 재생 후 다음 큐 항목 06으로 자동 전환되어 재생 위치가 13초까지 진행됨을 확인하고 일시 정지했다. 기기에서 나는 소리를 청취한 검증은 아니다.

최종 설치 앱에서 복구된 Viola & Piano 02번은 X100 출력으로 73초 이상 진행됐다. 이어 이 Mac 출력으로 전환한 뒤 자동으로 후속 트랙까지 진행하여 05번 재생 위치가 68초에 도달함을 확인했다. 검증 후 재생 큐를 비우고 X100 출력을 복원했다. 설정의 통계 화면에서도 최신 실패 목록 336건과 Anna Prohaska의 과거 파일 없음 항목 제거를 확인했다. 통계 화면의 현재 표시 대상은 5,329앨범·83,080곡이며, 아래 보존 검사 수치는 숨겨진 이전 기록을 포함한 전체 DB 행 수다.

시험 중 생성된 경로 표기 중복은 사전 DB 백업과 메타데이터·사용자 참조 비교 후 정리했다. 기존 ID, 즐겨찾기, 작품 연결 보존 여부는 최종 운영 DB와 전환 전 백업을 비교해 확인했다. 인증정보는 소스·로그·진단 JSON에 포함하지 않는다. 원본 서버에는 쓰기 작업을 하지 않았다.

진단 JSON과 최종 집계는 `~/Library/Application Support/Resonance/SMBValidation-2026-10-05/`에 보존한다. 이전 앱과 변경 전 SQLite 백업도 보존했다.

남은 336건은 **FLAC 원본 문제 4건과 미지원 APE·CUE 332건**이다. Music2 최종 재검사는 앞선 검색의 ID3 호환성 오류 159건과 다른 검증 프로세스의 동시 DB 사용 중 발생했던 일시적 잠금 실패 4건을 복구했다. 최종 기록에는 DB 잠금 오류가 없다. 스캔 및 재생 단계에서 NAS 원본에는 쓰지 않았다.

시작 바이트가 0이라는 결과를 파일 전체가 0이라는 뜻으로 확대하지 않는다. HIMARI의 0바이트 파일은 중간 진단에서 확인됐으나, 이후 전체 재검색에서는 해당 폴더 자체가 서버 목록에서 사라졌다. 기존 데이터는 보존하고 현재 목록에서만 제외했다.

최종 DB는 5개 루트·5,332앨범·83,106트랙·27개 설명을 보유한다. 기존 3,452앨범·53,481트랙·24개 설명의 ID 손실은 0이며, 즐겨찾기·사용자 수정·작품 연결 손실도 0이다. 기존 경로와 정규화 동등한 신규 중복은 0, SQLite 무결성은 `ok`, 외래 키 위반은 0이다. 데이터 보존 수치는 전체 DB 행 기준이다.

최종 설치 번들의 서명·동적 라이브러리 연결 및 `git diff --check`를 확인했다. 설치 DB의 쿼리 계획도 `searchContent_albumID` 인덱스 사용을 확인했다. 최종 근거는 `final-library-audit.json`, `remaining-issues.csv`, 원본 문제 4개만 담은 `remaining-flac-issues.csv`, `final-tests.log`에 남겼다.

## 범위와 제한

처음 선택한 곡은 전체 다운로드가 끝날 때까지 준비 대기가 있다. 실제 스캔과 재생 속도의 마운트 대비 우열은 측정하지 않았다. FLAC 이외의 원격 태그 파서, 원격 부클릿 다운로드, 대규모 SMB 변경 알림은 이번 범위에 없다. SMB 원본은 읽기만 수행한다.

## 앨범 목록·커버 수집·상세 이동 후속 수정

- Scriabin은 첫 페이지의 120번째 앨범이었다. 다음 페이지를 수동 버튼으로만 읽던 동작을 스크롤에 따른 자동 추가 로딩으로 바꾸고, 중복 요청을 막고 한 항목을 더 조회해 실제 다음 페이지 유무를 판정한다. 목록과 하단 상태를 하나의 지연 스택에 배치했다.
- 설치 앱에서 연속 스크롤로 마지막 `Ülo Krigul: Liquid Turns`와 **5,329개 앨범 표시**를 확인했다. 원본 DB의 전체 행 수와 현재 표시 대상 수는 구분한다.
- 앱 시작과 폴더 스캔 완료 시 누락 커버를 백그라운드 수집한다. 화면에 보이는 커버도 자동 요청하며, 최대 2개 작업·동일 앨범 요청 병합·실패 재시도 간격을 적용한다. 별도 SMB 세션을 사용하고, 결과는 썸네일 파일과 DB 참조로 저장해 재실행에도 재사용한다. 사용자 지정 커버는 보존한다.
- 앨범 폴더뿐 아니라 `CD1`·`CD2`의 이미지도 찾고, 이미지로 열 수 없는 후보는 다음 후보 또는 내장 FLAC 그림으로 이어간다. 파일/이미지 크기 상한은 유지한다.
- 캐시 정리는 현재 앨범에서 참조하지 않는 이미지를 먼저 제거한다. macOS 임시 폴더의 `/var`와 `/private/var` 표기를 동일하게 비교한다. 설정 및 기본 커버 캐시 한도는 사용자 요청에 따라 **2,048MB**로 늘렸다.
- 감상 노트 및 하단 플레이어의 커버를 접근성 이름과 도움말이 있는 버튼으로 바꿨다. 두 버튼 모두 `Gabriel Fauré` 상세 화면으로 이동함을 실제 설치 앱에서 확인했다. 곡·일시정지 위치 531.395초·X100 출력·음량 0.8이 유지됐다.
- 전체 테스트 81개 중 실행 76개 통과, 조건부 5개 생략. 후속 캐시 정리·디스크 폴더 커버 검사 2개도 통과했다. 앱 빌드와 번들 서명 검증을 통과했다.

최종 설치 빌드의 번들 파일·서명이 일치하고, 운영 DB의 캐시 설정은 2,048MB다. 이전 수집에서 첫 120개 모두 커버가 저장됨을 확인했다. 이후 기존 512MB 정리가 참조 중인 캐시를 제거한 사실을 확인하여 참조 없는 캐시 우선 정리로 보완했다. 현재 운영 DB에서 4213개 앨범의 로컬 커버를 확인했고 1116개가 남아 있다. 최종 빌드는 macOS Keychain 확인을 기다리고 있으므로 전체 커버 복구 완료로 보고하지 않는다. 상세 목록은 앱 저장 폴더의 `SMBValidation-2026-10-05/artwork-update-audit.json`에 보존했다.
